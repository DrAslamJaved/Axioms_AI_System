# Architecture decisions for the Foundation MVP

## What is implemented now

The supplied design specifies nine agents, Redis Streams, retrieval memory, external
connectors, and cloud deployment. These are appropriate end-state components, but
enabling them all before an evaluated core would make failures difficult to diagnose.
The MVP therefore implements an auditable execution path:

1. Typed request ingestion.
2. Deterministic and reviewable task routing.
3. Lecture and writing draft agents with explicit limitations.
4. Persistent task episodes in SQLite.
5. Mandatory owner approval prior to release.

## Deliberate deferrals

| Design element | Phase | Prerequisite |
| --- | --- | --- |
| LLM provider | 1.1 | Prompt/version registry, budget limits, red-team tests |
| Chroma/retrieval | 2 | Document consent, provenance metadata, deletion workflow |
| Research sources | 2 | Per-source API keys, citation/evidence contract |
| Redis Streams | 2 | Idempotency keys, retry/dead-letter policy, trace IDs |
| Social/GitHub/Moodle tools | 3–4 | OAuth scopes, dry-run tests, explicit owner approval |
| Autonomous evaluation | 4 | Human-calibrated benchmark set |

## Corrections to the source specification

- arXiv is a preprint repository, not necessarily peer reviewed; peer-review status must
  be recorded per source rather than inferred from its discovery channel.
- Similarity scores cannot establish originality or satisfy an institutional plagiarism
  process. The system presents them only as a review signal.
- An LLM-generated proof, citation, or research claim is not verified merely because it
  was generated by a specialised agent. Verification requires recorded evidence.
- Personalisation data requires a consent, review, export, and deletion process. The
  MVP stores no inferred personal profile.
